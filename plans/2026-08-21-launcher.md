# flatland: the launcher's half of the boundary

D31, D44, D29 and what D16 leaves to this repository. Everything built so far
governs a shell that has *already been handed* a policy. Nothing decides what
that policy should be, and one of its inputs — `HOME` — is still a fail-open
hole D31 named on day one.

**Status: implemented.** See "Where it landed" at the end.

## What is actually this repository's

D16 reads as one milestone and is two. Most of it is a *justfile* question:
resolving the `import`/`mod` graph up front, `set fallback`'s second upward
walk, `dotenv`, `[working-directory(...)]`, and D30's trampoline. None of that
code lives here — flatland is the shell and the namespace, and the justfile
scanner is rocjust's.

What this repository owns is the mechanism underneath: **a bounded search, a
grant derived from its answer, a persistent per-project home, and a record of
what the user consented to.** D44 already says the discovery strategy is
configurable "because this platform is meant to carry more than rocjust", so
building it here as a mechanism with the marker set supplied by the caller is
the shape the entry asks for.

Stated up front so the milestone is not read as delivering D16: **grant
derivation from a justfile graph is not in it.**

## The leaks, measured

D6 claims host paths are *unnameable* — "an escape has no syntax". Under the
strongest policy this tree can express (`--mount`, `--closed-world`,
`--restrict-builtins`), three of the five leaks D6 itself lists still answer:

```
$ env -u HOME brush --mount /work:DIR:rw --closed-world --restrict-builtins \
      -c 'echo ~; echo ~root; echo $SHELL'
/Users/grayrest
/var/root
/bin/zsh
```

The first is D31's: `home_dir` (`brush-core/src/shell/fs.rs:155-162`) falls back
to `users::get_current_user_home_dir()` when `HOME` is unset — the one place in
the tree that fails *open*. None of the three is a filesystem escape; `cd ~`
fails. They leak host *layout*, which is what D6's sentence forbids.

**Two of the five are already closed, by D11 rather than by design.**
`compgen -u` prints `grayrest` and `compgen -A hostname` prints the machine
name — under `--closed-world` alone. Under `--restrict-builtins` they do not,
because `compgen` is not on the allowlist. That is a real interaction and a
fragile one: the leak is closed by a list whose purpose is something else, so a
future decision to admit `compgen` reopens it silently.

## What is already true

- **Nothing derives a policy.** `--mount` is parsed from the command line
  (`build_mount_table`, `entry.rs`) and that is the entire input path. There is
  no launcher config, no discovery, no ceiling.
- **The config loader is the right shape and the wrong scope.**
  `brush-shell/src/config.rs` already reads a TOML file from the platform
  config dir via `etcetera`, before any shell exists, and its own comment calls
  it "the launcher's own configuration". D16's ceiling belongs there.
- **`etcetera` gives the state dir D31 needs** for `/home/user`'s persistent
  backing, and the config loader already depends on it.
- **`RcLoadBehavior` is the knob D31's correction names**, separate from
  `ProfileLoadBehavior`, which is consulted only for login shells.
- **The mount table can express most of what a grant needs.** Nested virtual
  mount points with differing access build and resolve by longest match; what it
  cannot express is an *enclosing* read-only tree overlapping a read-write one,
  which is D16's `import '../shared.just'` case and therefore not this
  milestone's.

## The change

**Step 0 — delete the passwd fallback.** D31 says "delete it, do not shadow
it". `home_dir` returns `None` when `HOME` is unset, and every caller already
handles that — `~` with no home is an error, not a host path. It is first
because it is the only *fail-open* behaviour left in the tree.

~~This is the one step that is pure subtraction.~~ **Measured, and it is not.**
The compatibility harness runs with `HOME` unset and bash resolves `~` through
the passwd database, so deleting the fallback outright fails two cases. It is
therefore removed *under a policy*, where the passwd database is outside the
namespace and the answer is a genuine leak — and kept under identity, where the
host **is** the namespace, `/etc/passwd` is a nameable path, and nothing leaks.
The condition is exactly "is the passwd database outside the namespace".

**Step 1 — `$SHELL` and `~user` answer from the namespace.** The remaining two
measured leaks. `~user` for a user that is not the session's own resolves to
nothing rather than to the passwd database; `$SHELL` names the launcher as the
namespace sees it, or is unset. Both are D6 corrections that were recorded and
never made.

**Step 2 — a bounded search, as a mechanism.** Walk upward for a marker from a
configurable set, stopping at `$HOME`, the filesystem root, or a platform system
tree. **The stop list is enumerated per platform, canonicalized and
case-folded** — D44 is emphatic and specific here, because `/tmp` canonicalizes
to `/private/tmp` on macOS and a list containing `/private` kills discovery for
every temp-directory checkout, including this repository's own scratch
worktrees. Home is resolved through the same helper the shell uses, never
through `HOME`, because on Windows `HOME` is normally unset and the stop would
silently vanish.

**Step 3 — the bound is a predicate on the answer, not on the walk.** D44's own
correction, and the reason it matters is that three routes reach a root without
searching. The rule is: the resulting directory must lie strictly below a marker
that is itself strictly below every stop — checked identically however the
directory was arrived at, including when it was named outright.

**Step 4 — the marker's own directory is carved out of the grant.**
`.git/config` carries `core.pager`, `core.fsmonitor` and `!sh -c` aliases, and
git runs what it finds there at the user's next command. Expressible today as a
read-only mount nested inside the read-write one, which is the nesting the mount
table already supports.

**Step 5 — `HOME` is a per-project mount.** `/home/user` backed by a directory
under the user's state dir, keyed so one project's home is invisible to another,
with XDG paths as subdirectories. **And rc loading defaults off under a
restrictive policy**, because a persistent writable home plus rc loading is a
project-scoped persistence vector: a hostile repository drops `~/.bashrc` once
and gets execution on every later run.

**Step 6 — the trust store.** Keyed by the *granted set*, so a subset
auto-accepts and narrowing never re-prompts. Non-interactive runs fail closed
with an error naming the exact `--mount` flag that would grant what was asked
for. **No approve-all flag**, per D29 — one would become a copy-pasted line in
every pipeline, on exactly the machines where this matters most.

## Gates

1. **The three measured leaks, inverted**, under the same flags. And a control:
   the same commands under identity still answer as bash does, or the compat
   suite is what breaks.
2. **`compgen`'s leaks are closed on their own**, not by the allowlist. The test
   admits `compgen` explicitly with `--allow-builtin` and still expects nothing,
   so the coverage does not evaporate the day the list changes.
3. **The stop list is tested against canonicalized temp paths on macOS** — the
   specific failure D44 predicts, which a list written from intuition produces.
4. **A marker at or above a stop does not rescue the walk.** The dotfiles-repo
   case: `$HOME` as a source-control root must fail, not grant `$HOME`.
5. **All four routes to a root are held to the predicate**, including the two
   that never search.
6. **The marker's directory is not writable** from inside the derived grant.
7. **A subset of a stored grant does not prompt; a superset does**; and a
   non-interactive superset fails closed with the flag in the message.
8. **Not vacuous**: assert a *derived* grant against the mounts it produces, not
   merely that discovery returned something.

## Risk

**The stop list is the whole bound, and it is a hard-coded list per platform.**
D44 spends more words on it than on the walk for good reason: every mistake in
it either kills discovery for legitimate checkouts or admits `$HOME` as a
grant. It cannot be derived, so it has to be tested against real canonicalized
paths rather than the strings someone expected.

**Step 5 makes a writable directory that outlives the run.** That is the point —
caches survive — and it is also a new persistence surface that did not exist
before this milestone. The rc default is what keeps it from being an execution
surface, which makes that default load-bearing rather than a convenience.

**D29's store is consent state, and consent state that is wrong in the
permissive direction is silent.** A subset check that is subtly too generous
never prompts and never reports.

## What stays behind

D16's grant derivation from a justfile graph, and everything it needs: the
host-side scanner, the guest loader that fails closed on anything unresolved,
`set fallback`, `dotenv`, `[working-directory(...)]`. D30's trampoline. The
enclosing-tree mount case, which needs either per-path access rules or a
read-only common ancestor, and which D16 records as genuinely inexpressible
today.

## Where it landed

Written after the fact. The plan above is left as written so the difference is
visible.

### Built as planned

Steps 0–6 and gates 1–5, 7. The three measured leaks are closed and their
controls hold; `compgen`'s two are closed by the namespace rather than by D11's
list, with a case that admits `compgen` explicitly and still expects nothing;
the bounded search, the predicate on the answer, the marker carve-out, the
per-project home and the trust store all exist, wired to `--project DIR`.

### Built differently

**Step 0 was not pure subtraction, and the plan said it was.** Deleting
`home_dir`'s passwd fallback outright fails two compatibility cases, because the
harness runs with `HOME` unset and bash resolves `~` that way. It is removed
under a policy and kept under identity — where the host *is* the namespace,
`/etc/passwd` is nameable and nothing leaks. That needed a name for the
question, so `Shell::is_confined` is now the namespace-axis twin of
`BuiltinPolicy::is_open`.

**`$SHELL` was not synthesis.** The plan assumed the leak was in
`wellknownvars`'s synthesis path. It is *inherited*, and D21 puts `SHELL` in the
"synthesized from policy, never inherited" class — so the removal belongs where
the policy is installed, in the launcher, which is where D21's remaining
variables will need values to synthesize from.

**The marker could not be mounted read-only.** `MountTable::build` rejects
overlapping host directories, correctly: two mounts of one inode tree let
`ln /work/.git/config /work/x` give a read-write name to a read-only inode, the
same hazard D16 raises against per-path rules. The marker is **shadowed** by an
empty read-only directory instead — ordinary mount semantics — so the host
directories are disjoint and the real marker has no name at all. That satisfies
D44's words rather than only the writability half of its reasoning.

### Not built

~~**Gate 6 has no test.**~~ **Built since**, as
`no_write_route_reaches_the_marker`. Unreachability is the stronger property for
*reading* and says nothing about writing, which is what D44's reasoning is
actually about: a grant that cannot read `config` but can drop a
`hooks/pre-commit` has closed nothing. Every write route in the facade is
enumerated rather than sampled, because a read-only mount is enforced per call.

Two things the writing showed. The indirect route is closed one step earlier
than expected -- a symlink inside the writable tree pointing *at* the mount
point is refused at creation, so there is no name to write through rather than a
name that is written through and refused. And `rename` and `hard_link` are
refused by the **mount boundary** rather than by the access mode, which is the
stronger refusal: it does not depend on the shadow having been mounted
read-only, only on it being a mount at all.

The case also asserts that neither the host's real marker nor the shadow gained
an entry, which an error-only assertion cannot: every call failing is consistent
with one of them having succeeded somewhere else first. The shadow matters
specifically because it is one empty directory shared by every project on the
machine, so a write landing there would be a channel *between* projects rather
than only an escape from one.

~~**Gate 8's "not vacuous" is partial.**~~ **Built since**, as
`a_derived_grant_is_the_namespace_the_fixture_asks_for`. It runs the pipeline
the launcher runs -- discovery upward from a nested directory, then derivation
-- and compares the whole mount set to an expectation built from the fixture's
own layout. The expectation **duplicates `home_key`'s hash and
`launcher_state`'s path on purpose**: composing the helpers under test would
assert only that the code agrees with itself, which is the failure mode the gate
is named after. Two fixtures rather than one, because a fixed expectation is
satisfied just as well by a pipeline that ignores its input.

Both are unit cases against the derived namespace, not end-to-end runs of
`--project`. There is no end-to-end case for that flag and cannot easily be one:
a non-interactive run fails closed unless the grant is already trusted, and the
trust store is the *user's*, so a test that made it pass would be writing
consent into it.

~~**`--project` implies nothing.**~~ **Changed since: it implies both.** The
axes are still separate -- what changed is who is choosing. `--mount` is a
caller composing them by hand, and defaulting one of the others would silently
alter a namespace they wrote out; `--project` derives the whole policy from a
directory, so leaving two of its three axes wide open made the safe spelling the
longest one. `--open-world` and `--unrestricted-builtins` turn them back off,
and they are two flags rather than one because needing the host's compiler is
not a reason to get `enable` and unrestricted `kill` back. Each conflicts with
its positive twin, so a command line cannot ask for both and have one of the two
spellings silently do nothing.

**One consequence to state, because it is a cliff rather than a slope.**
`--closed-world` in a build without `experimental-bundled-coreutils` leaves a
shell that can run nothing external *and* has no bundled `cat` -- and that
feature is not in the default set. So `--project` on a stock build is now a
shell with no external commands at all. That is `--closed-world`'s existing
behaviour rather than something this default introduced, but the default is what
makes it reachable without asking for it.

### Found here, fixed since

**`ls <dir>` failed in any confined shell** — `ls /work` reported a bare "No such
file or directory" while `cd /work && ls` worked and `ls /work/f.txt` worked. It
predated this milestone (it reproduced on the older `--mount` path) and was not
the broker: the child had its namespace, since `cat /work/f.txt` worked. Probed
far enough to rule out the obvious causes and recorded with that evidence rather
than half-fixed.

Fixed in `d66c29f1`. The bare message was the clue that mattered: no path means
no `LsError::IOErrorContext`, which leaves a `?` propagating an `io::Error`
straight out of `list_with_output`. That is
`uucore::fs::FileInformation::from_path`, the loop-detection identity `ls` takes
for each directory argument before it descends, and it was back on
`rustix::fs::{stat,lstat}` — asking the host. Not a gap but a **regression**:
that call was routed in step 7 of the uucore fork, and the re-vendor in
`3eb5b2e1` reverted the patch along with `safe_copy`'s `open` and
`safe_traversal`'s `DirFd::open`. `cp` and `du` were broken the same way and by
the same commit. `RESIDUAL-PATCHES.md` had described all three as applied the
whole time, which is the file doing its job and nobody reading it.

This section's own conclusion about the three inherent `Path::metadata` calls
was half right and worth correcting. Routing them did not change *this* symptom,
which is why they were left alone — but they were a second, independent bug with
their own failing cases, not a false lead: `ls <symlink-to-dir>` printed the
link's own name instead of listing its target, and anything under `-L` failed
outright with `cannot access '/work'`. "No failing case" meant "no failing case
*for this symptom*"; the right next question was what else those calls decide.
They are routed in the same commit.

The deeper finding was the gate, not the bug. `check forks` stayed green through
all of it, because it runs each fork's upstream suite on the host under an
identity session, where routed and unrouted behave identically — the property
that makes it a good rebase metric is the reason it cannot see confinement. No
gate enabled `experimental-bundled-coreutils` or `coreutils.all` either, so the
bundled utilities were never exercised by default. The forks are now linted for
ambient authority against `forks/UNROUTED.txt` (`09cd93bd`), and `check forks`
fails a fork that does not compile (`8a26af67`) — which is how `sed`'s suite had
been silently uncompilable since it landed.
